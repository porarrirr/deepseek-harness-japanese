# Agent Note: 公共文档使用推导的三语配对

Status: implemented

[English](2026-08-20-public-japanese-translation-pairing.md) | 中文

## 问题

本仓库拥有范围很广的双语文档语料，而文档站发布的页面集合较小，并且这些页面还需要日语。对所有语料要求日语会把翻译工作扩展到私有的贡献者和 package 文档，而手写的公开推进清单又可能与 `website/docs.ts` 脱节。

## 决策

配对门禁从 `website/docs.ts` 的 `docsPages` `source` 值推导公开源集合，把 locale 后缀规范化为一个无后缀英文锚点，并去重站点 locale 的条目。

公开源使用 `foo.md`、`foo.zh.md`、`foo.ja.md` 和 `foo.i18n.yaml`。其 sidecar 必须严格包含三个所有者 blob hash。范围内的其他源继续使用双语的 `foo.md`、`foo.zh.md` 和 `foo.i18n.yaml` 记录，并且严格包含两个 hash。

`.ja.md` 是译文一侧，不是源候选。配对路径规范化接受公开配对的四种产物，并把每一种解析为 `foo.md`。公开源、中文和日语的切换行都有明确的规范形式；生成英文源继续免除切换行。

生成区域校验、合并组合、冲突解决和 Markdown 围栏派生校验使用同一个公开语言集合。公开生成页面在日语一侧存在时也会接收生成区域；缺少这一侧仍由配对门禁报告。

[双语配对 Agent Note](2026-07-02-bilingual-docs-and-pairing-gate.md) 继续负责语言同权、blob 恢复、结构签名和双语默认值；本文负责公开语言集合的拆分。

## 考虑过的替代方案

- **要求范围内的每篇文档都有日语。** 否决：非公开的 package、贡献者和流程文档继续采用双语维护约定，公开要求的读者范围更窄。

- **维护手写的公开推进清单。** 否决：清单可能与发布清单分叉，而 `docsPages` 已经标识网站投影的每个页面。

- **建立独立的日语目录或网站 locale 清单。** 否决：locale 目录会拆分仓库相对链接并重复发布所有权；现有兄弟文件约定让源链接和配对记录保持在同一目录。

## 后果

在 `docsPages` 中添加或移除页面会改变其源文件所受的语言集合，不需要第二份推进编辑。公开 sidecar 与合并记录多一个所有者 hash，而非公开记录保持不变。

仓库能够在日语译文落地前报告缺少的公开页面，公开页面也不能用双 hash 记录确认。生成英文输出仍是字节级真源，因此生成页面仍只免除英文切换行。
